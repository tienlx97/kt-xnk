## MD3 brand color/theme derivation (2026-08-06/07)

Derived the kt-xnk Astryx theme (`src/shared/components/theme.js`,
`defineTheme`) from the brand logo (`public/images/logo-dn-group.png`):
sampled seeds teal `#247768` and red `#c2252a`. Chose teal as the Material
Design 3 *primary* seed and red as *secondary* — red as the dominant accent
read too harsh/glaring across filled surfaces (inputs, primary buttons), so
teal carries the brand and red is kept for lower-emphasis/secondary use
(this was a mid-course swap: red started as primary, then got demoted).
Tonal palettes were generated in CIE Lab space (tone = L*, hue/chroma held
from the seed) plus a standalone error seed (`#b4271f`/`#b3261e`). All
on-color pairings (e.g. `--color-on-accent` on `--color-accent`) were
verified ≥ 4.5:1 contrast (WCAG AA). Project is light-theme only (no dark
mode), so every token in `theme.js` is a single value, not Astryx's
`[light, dark]` tuple form. 18 tokens overridden total (accent group,
surfaces, text/icon, borders, error group); everything else (success/warning,
categorical tag colors blue/cyan/gray/green/orange/pink/purple/red/teal/
yellow, structural tokens) deliberately left at Astryx/theme-neutral
defaults — universal status-color conventions read faster than a
brand-consistent reinterpretation would. Also wired `Button
variant="secondary"` to MD3's secondaryContainer/onSecondaryContainer
pairing via the theme's `components.button` override, since Astryx's
built-in secondary variant defaulted to neutral gray, not the brand.
Full derivation + contrast numbers: `harness/PROGRESS.md` entries from
2026-08-06 21:44 through 2026-08-07 00:08; decision record in
`openspec/project.md` Conventions → Color.

## Feature-based front-end architecture migration (2026-08-07)

Replaced the 6-layer backend-shaped architecture
(`types→config→repo→service→runtime→ui`) with a feature-based front-end
architecture, per explicit user direction: this repo is confirmed
**front-end only** — the backend (data access, business logic) lives in a
separate project, so `repo/service/runtime` were dead weight (empty since
bootstrap). New shape: `src/features/<feature>/{types,config,api,hooks,
components}` and `src/shared/{types,config,api,hooks,components}`, layer
order `types → config → api → hooks → components` inside each tree.
`api/` replaces `repo` (calls to the separate backend project); `hooks`
replaces `service` (client-side state/logic); `runtime` was dropped
outright since `src/app/` (Next.js routing/wiring) already plays that role
for the whole app. Features are fully isolated (no cross-feature imports at
all — share via `src/shared/` instead) and reachable from outside only via
their own `index.js`, enforced by new dependency-cruiser rules in
`harness/structure.rules.cjs` (`no-feature-to-feature`,
`no-shared-to-feature`, `no-deep-feature-imports`), with fixture coverage in
`harness/tests/structure-rules.test.cjs`. Migrated: `src/ui/hero.js` →
`src/features/home/`; the design-system showcase page's sections →
`src/features/design-system/`; header/footer/theme/site-config/shared types
→ `src/shared/`. Full rationale and alternatives considered:
`docs/adr/0003-feature-based-architecture.md`; execution record:
`openspec/changes/feature-based-architecture/` and `harness/PROGRESS.md`
(2026-08-07 01:56). `harness/GOLDEN_RULES.md` bumped v1→v2 for this.
